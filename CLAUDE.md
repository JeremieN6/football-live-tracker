## Objectif Final
Construire un SaaS "Match Report AI" pour coachs amateurs : suivi live des evenements match + rapport tactique IA exploitable apres match. Cible a terme : plusieurs clubs, chacun avec plusieurs equipes (ex. Equipe 1, Equipe reserve) et plusieurs coachs, cloisonnement strict des donnees par club/equipe.

---

## Stack Technique
- Frontend : Vue 3 + TypeScript strict + Vite 6
- UI : Tailwind CSS v4 + composants custom tracker
- State : Pinia
- Routing : Vue Router 4 (routes protegees)
- Backend : Supabase (Postgres, Auth, Realtime, Edge Functions)
- IA : Anthropic Claude (Haiku) via Edge Function `generate-report`

| 11/09/2026 | Le "renfort" d'un joueur dans une autre equipe du club n'est pas un historique a saisir a la main | Detecte automatiquement en comparant l'equipe du match (`matches.team_id`) a l'equipe actuelle du joueur (`players.team_id`) au moment de l'affichage du profil — plus simple qu'une table d'historique, coherent avec la demande de l'utilisateur ("un joueur peut jouer dans une autre equipe ponctuellement, ca doit etre marque quelque part") sans complexifier le modele. |
| 11/09/2026 | Phase B : lecture de `players` club-wide (tout membre actif voit tous les joueurs du club), mais ecriture (creer/modifier/archiver) limitee a l'equipe du joueur | Sans ca, un coach de l'equipe 1 ne pourrait pas voir le nom d'un joueur de la reserve appele en renfort dans un de ses matchs (feature "renfort" de la Phase A) — la donnee "qui est ce joueur" est peu sensible et utile a tout le club, contrairement aux donnees de match (evenements, effectif convoque, rapport) qui restent strictement limitees a l'equipe. |

| 11/09/2026 | Le role OWNER garde un acces total (lecture+ecriture sur tout le club), meme si dans la vie reelle il representera le president qui ne fera que consulter | L'utilisateur (createur de l'outil) est actuellement le seul compte reel et bricole toute l'application avec ce role — le restreindre a de la lecture seule maintenant l'auto-bloquerait pendant la construction. | 11/09/2026 | Ajout des roles PLAYER/OTHER (lecture seule sur leurs equipes) au moment de l'invitation, sans construire la hierarchie complete de roles ni un vrai espace joueur | L'utilisateur a confirme vouloir, a terme, un vrai systeme ou le role choisi a l'invitation determine les droits (et un "joueur" aura bien une case dediee) — mais en pratique aucun vrai joueur n'est invite pour l'instant ("on est encore en train de coder"). | 11/09/2026 | Nouveaux clubs en attente de validation manuelle (`clubs.status`) plutot qu'un systeme de code d'invitation ou de verification de nom pour empecher les faux clubs | L'utilisateur ne voulait pas que n'importe qui cree un club actif (l'outil n'est pas voue a etre du B2C) mais n'etait pas sur de la bonne approche (hesitation sur la gestion des doublons de nom). Un nom unique ne prouve rien (n'importe qui peut se faire passer pour "FC Tourcoing") : la vraie protection est qu'un humain (l'admin) voie et valide chaque nouveau club avant qu'il soit utilisable, ce qui resout aussi le probleme des doublons au passage (l'admin le remarque en validant). Solution la plus simple compatible avec le fonctionnement actuel du projet (validations manuelles via SQL Editor) plutot que de construire un systeme de code d'invitation pour le tout premier club, qui aurait ajoute de la friction sans mieux resoudre le probleme. |
| 11/09/2026 | Reinitialiser tous les stores Pinia lies a un compte/club des que l'identite change (`onAuthStateChange`), plutot que de compter sur un rechargement complet de page entre deux comptes | Trouve en testant la validation de club : se deconnecter puis se reconnecter sous un autre compte dans le meme onglet laissait les anciennes donnees (club, equipes, joueurs...) en memoire dans les stores tant qu'une vue ne les re-fetchait pas explicitement, ce qui a fait bugger la garde `/pending` (elle lisait le club perime de l'ancien compte) et aurait pu, plus largement, laisser apparaitre les donnees d'un compte precedent apres un changement de compte sans rechargement. Centraliser le reset dans `auth.store.ts` (suivi de `currentUserId`) est plus fiable que de compter sur chaque vue pour re-fetcher au bon moment. |
